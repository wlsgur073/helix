Method: one auditor, walking `SECURITY.md` section by section, enumerating every sentence that
asserts a property of the shipped system. Each claim is checked one of three ways, and the way is
recorded rather than smoothed over:

- **`test-pinned`** — a committed test recovers the value from the code by executing or searching it
  and then requires `SECURITY.md` to state that value. These claims are *continuously* verified: the
  code cannot move underneath the sentence without the suite going red. The lock is
  `test/docs/shipped-claims.doc.test.ts` unless another file is named. Re-run at `0bcd4d7`:
  **44 passed / 44**, including its own premise case (`staleBundles()` empty — `bin/` is a
  byte-identical rebuild of `src/`, which is what lets a `src/`-level probe speak for the bundle a
  user runs).
- **`executed`** — this audit ran something and observed the result. The command and the observation
  are given.
- **`read`** — this audit read the code and reasoned. Nothing mechanical holds these; they are
  listed again, in full, under *What is not covered*.

Verdicts are `accurate as written`, `accepted empirical statement` (true, but with no in-repo
mechanism to check — a live observation or an off-tree fact), or **`FALSE`**. There are no
`corrected` verdicts in this record **by design**: a documentation edit at this point moves a
claim-block id that the release's candidate receipt pins, so the two corrections this sweep found are
written out below as exact replacement text and left unapplied. Applying them is a release-gate
decision, not an auditor's.

### Correction 1 — FALSE: the open() leg does not suppress, and the suppressed set is six codes, not four

**Current text (`SECURITY.md:383-390`), verbatim:**

> **errno alone, never on the message**: if the directory cannot be opened at all, or the fsync call
> itself fails with `EINVAL`/`EISDIR`/`ENOTSUP`/`EOPNOTSUPP`, the platform genuinely cannot fsync a
> directory (some filesystems, and Windows, reject it outright — `ENOTSUP`/`EOPNOTSUPP` are a second
> pair some filesystems return instead of `EINVAL`/`EISDIR`; the same numeric value on Linux but
> distinct symbols elsewhere) and the failure is suppressed

**What ships (`src/memory/fs-ops.ts:43,64-83`):**

```ts
const DIR_FSYNC_UNSUPPORTED = new Set(['EINVAL', 'EISDIR', 'ENOTSUP', 'EOPNOTSUPP', 'EPERM', 'EACCES']);
…
  try { dfd = sys.openSync(dir, 'r'); }
  catch (e) { if (platform === 'win32' || isUnsupported(e)) return; throw e; }
  try { sys.fsyncSync(dfd); }
  catch (e) { if (!(platform === 'win32' || isUnsupported(e))) throw e; }
```

**Measured**, by driving `fsyncDir` through its own injectable `DirFsyncSyscalls` seam with
`platform = 'linux'`:

| leg | `EINVAL` | `EISDIR` | `ENOTSUP` | `EOPNOTSUPP` | `EPERM` | `EACCES` | `EIO` | `ENOSPC` | `EMFILE` | `ENOENT` |
|---|---|---|---|---|---|---|---|---|---|---|
| open() | suppressed | — | — | — | **suppressed** | **suppressed** | **propagated** | **propagated** | **propagated** | **propagated** |
| fsync() | suppressed | suppressed | suppressed | suppressed | **suppressed** | **suppressed** | propagated | propagated | — | — |

Two independent falsehoods:

1. **"if the directory cannot be opened at all … the failure is suppressed" is false.** An open
   failure propagates unless it carries a `DIR_FSYNC_UNSUPPORTED` code or the platform is win32.
   `EIO`, `ENOSPC`, `EMFILE` and `ENOENT` on the open all throw. The sentence describes the
   **superseded** 2026-08-06 rule; `fs-ops.ts:59-63` says so in as many words ("The open() leg
   propagates too (2026-08-11, superseding the 2026-08-06 ruling that swallowed every open
   failure)"), and `test/memory/fs-ops.test.ts:32-34` pins the new behaviour under the name *"a
   missing directory PROPAGATES on POSIX"*. So a shipped, green test contradicts the shipped
   document. This direction is *pessimistic* — the document confesses a silent-durability-loss path
   the code does not have — but a security document that misdescribes its own durability boundary is
   wrong either way, and a reader deciding whether to trust an acknowledged append is given the
   wrong rule.
2. **The suppressed class is six codes, not four.** `EPERM` and `EACCES` are in
   `DIR_FSYNC_UNSUPPORTED`, and `isUnsupported` is applied to **both** legs (`:73` and `:79`), so a
   directory fsync that fails `EPERM`/`EACCES` is silently swallowed. The next sentence —
   "Any other failure (`EIO`, `ENOSPC`, and their class) … now **propagates**" — is therefore false
   of those two codes. This direction is *optimistic*: it promises propagation where the code
   swallows, which is the dangerous way round. Note the source's own comment (`fs-ops.ts:36-38`)
   claims `EPERM`/`EACCES` "join them for the open() leg", which the fsync leg's shared
   `isUnsupported` call contradicts; that comment is wrong too, but it is a code comment and outside
   this audit's remit to change.

**Recommended replacement for `SECURITY.md:383-390`** (the surrounding sentence structure is
preserved; only the classification is corrected):

> **errno alone, never on the message**: if the fsync call, or the `open` that precedes it, fails
> with `EINVAL`/`EISDIR`/`ENOTSUP`/`EOPNOTSUPP`/`EPERM`/`EACCES`, the platform or the directory's
> standing permissions genuinely cannot fsync a directory (some filesystems reject it outright —
> `ENOTSUP`/`EOPNOTSUPP` are a second pair some filesystems return instead of `EINVAL`/`EISDIR`; the
> same numeric value on Linux but distinct symbols elsewhere) and the failure is suppressed. Windows
> cannot open a directory for reading at all and stays wholesale best-effort on the same path.

The following sentence ("Any other failure (`EIO`, `ENOSPC`, and their class) … propagates") then
becomes true as written, and should additionally name the open leg: a directory that cannot be
opened for an `EIO`/`ENOSPC`/`EMFILE`/`ENOENT` reason throws rather than reporting success.

### Correction 2 — imprecise: the audit trail's directory fsync is suppressed on every append, not on first creation

**Current text (`SECURITY.md:394-399`), verbatim:**

> (`audit.jsonl`) is the one exception: it is documented best-effort/non-transactional already (see
