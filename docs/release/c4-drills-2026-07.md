## Findings & dispositions

- **F1 (docs defect, fix proposed):** `claude plugin update helix` — the exact command
  README's install section prints — fails on claude CLI 2.1.220 with `Plugin "helix" not
  found`; the `plugin@marketplace` form `helix@helix` is required. The name resolution is
  asymmetric: uninstall/disable/enable accept the bare name, update does not
  (`c4.1/22/23/25-*.log`). DISPOSITION: **FIXED @ d481893** (owner-approved) — README's update
  command and the runbook's end-user note now print the `helix@helix` form and record the
  asymmetry.
- **O2 (honesty observation, tracked):** maintenance actions are invisible by design today —
  `sweepOrphanTmps` returns a count every caller discards (live-confirmed for the stderr
  surface: the driver prints any server stderr and none appeared, `c4.3/21-*.log`; the
  no-metric/no-audit halves are code-verified at the discarding call sites — ledger.ts:80/:438,
  ledger-mac.ts:35, witness-store.ts:92), the auto-compaction cheap-gate's deferral
  `reason` is discarded at `store.ts:453` (a deferred compaction is indistinguishable from
  none; the `compaction-trigger.ts:11-12` doc comment claiming the reason "labels the
  compaction metric" is stale), and a parse-level corrupt-line skip surfaces nowhere except
  the permanent-erase gate (the witness alarm, not parse health, is what makes witnessed-range
  corruption visible). DISPOSITION: recorded as a tracked residual bundle (post-v0.1
  observability nicety); the stale comment is a one-line cleanup candidate the owner may fold
  into any future touch of that file.
- **O3 (wording nuance, tracked):** the write-block error and disclosure note say "re-drive
  the operation, or run a re-baseline", but for a compaction-interrupted scope no MCP tool
  surface can re-drive (auto-compaction is suppressed while a journal is pending; manual
  compaction is not a tool) — the realistic user recovery is the ceremony, as the drill
  demonstrated. For an interrupted erase/rewrite reached through a tool, re-drive IS real.
  DISPOSITION: recorded; optional future wording tweak, not a blocker.
- **O4 (tool-surface observation, matches documented caveat):** at the raw MCP layer (stdio,
  no Claude Code host), `helix_memory_confirm` and `helix_memory_adopt` execute without any
  approval hand-shake — the host's tool-permission prompt IS the "explicit user approval" the
  disclosures refer to, and a local process that bypasses the host has filesystem power
  anyway (the unconfined-agent class already accepted in C3.2). No doc change needed; the
  drill record is the evidence that the boundary lives at the host layer.
- **O5 (operational note, runbook candidate):** headless launch-barrier verification
  (`claude -p` + one helix tool call) requires `--allowedTools
  "mcp__plugin_helix_helix__<tool>"` — without it the call is blocked in non-interactive
  mode (`c4.1/30` vs `31-*.log`). DISPOSITION: **FOLDED into the F1 commit @ d481893** — the
  runbook's verify step now carries the headless allow-listing note.
