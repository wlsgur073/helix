## How this document works

**This document is an execution record, not an essay.** Paste the command that was run and the
output that was observed at each step, and name the verdict row it answers. Never present
reconstructed output as an observation. If something is a summary, say that it is a summary.

**If the candidate moves, this whole file is `STALE`.** When a defect turns up mid-certification,
fix it, rewrite `v0.1-candidate-receipt.json` against the new candidate, and start this document
again from the top. There is no sound bookkeeping technique for carrying a row across changed
bundle bytes. That is why the cheap automated checks come first and the expensive manual ones last.

**The format follows `c4-drills-2026-07.md`.** Record the candidate commit, the 3-sha identity, the
load-path hashes, console logs with a sha256 manifest, and observations made in a fresh process.
Because that document was bound to `afc29c4`, its expiry could still be computed 187 commits later.

**Runs append; a completed run is never rewritten.** Each certification gets its own dated section,
and a prior one is the record of what was observed on that day. Corrections belong in a newer
section or in *Current state* above — never in the older run's text. Restructured 2026-09-09,
because until then every re-certification rewrote the header and stacked another banner on top,
leaving the file opening with three notices in the wrong order, naming a candidate that had been
retired twice.

Run it before Block A and again after Block E. **The release is not certified until it exits 0**, and
its output is the evidence that this document's own bookkeeping still holds. Paste both runs.

Added 2026-09-02, after measuring what its absence cost. Until that day `gatePasses` had **zero
production callers** — only its definition and one test, which says in terms that no passing assertion
can be made yet — so the gate ran only when somebody remembered to reason about it. Nobody had: all 74
rows were bound to candidate `01483ce9`, 111 commits behind HEAD, whose shipped bundle no longer
matched the tree, and no check anywhere emitted a signal. Two holes were open at once:

- **A row's `candidate` was a string nothing dereferenced** — the same shape `danglingClaims` already
  guards for `claimId`, one level up. `staleBinding` now compares every row against the receipt's
  candidate and every receipt-pinned artifact against its bytes on disk. The comparison target is the
  IMMUTABLE receipt, never HEAD: certification-only commits move HEAD without touching the shipped
  bundle, and a matching artifact never excuses a mismatched candidate.
- **The gate opened by DELETION.** `gatePasses` asks only that the table be non-empty and every row
  MET, so dropping the three unevidenced rows flipped it from `false` to `true` over the surviving 71
  — measured, not hypothetical, and precisely the invisible absence Block A's "zero silent skips"
  forbids. `missingRows` compares the ledger against an expected inventory the ledger does not
  control. **The receipt must carry `payload.rowIds` from the next cut onward**; a receipt without it
  is reported as unable to detect a deletion rather than passed over.

It is deliberately not a CI job and not a vitest case. A blocked RELEASE and a broken DEVELOPMENT
suite are different failures with different readers, and a check that is red on every push gets
normalised and then bypassed. The unit suite pins this logic on fixtures and stays green
(`test/inventory/release-binding.test.ts`, `test/inventory/certify-gate.test.ts`); this block is where
the real state gets reported, and it is expected to fail while the release is uncertified.
