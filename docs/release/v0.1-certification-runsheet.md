요약이라고 적는다.

바이트를 가로질러 행을 이월하는 건전한 장부 기법은 없다. 값싼 자동 검사를 앞에, 비싼 수기
검사를 뒤에 배치한 이유가 그것이다.

**서식의 선례는 `c4-drills-2026-07.md`이다.** 후보 커밋, 3-sha 정체성, load path 해시, 콘솔

## Block C — 복구 여정 — **통과** (2026-08-19, 일회용 사본)

`recovery-playbook.md`의 절차를 사용자처럼 따라갔다. **문서가 지시하는 명령을 그대로 실행하며,
실행되지 않는 명령은 그 자체가 `FAILED`이다.**

**fixture.** 가짜 `HOME` 아래에 배포 번들(`bin/helix-mcp.mjs`)을 구동하여 사실 두 건을 저장하고
하나를 `helix_memory_confirm`으로 승급시켰다. 따라서 서명 키와 상승 등급이 실재하는 상태이다.
관측된 초기 상태는 `DATA[Verified:global]| m_2fe00555…`와 `DATA[Fresh:global]| m_a3868b45…`이다.

- [x] **C1. 백업 → 빈 디렉터리로 복구**

  playbook §6의 단일 단위 형식을 문자 그대로 실행하였다.

  ```bash
  mkdir -p ~/backups
  tar -czf ~/backups/helix-global-$(date +%F).tar.gz -C ~ .helix
  ```

  문서가 지시한 `tar -tvzf` 검증에서 모드가 보존됨을 확인하였다. 서명 키가 `-rw-------`이다.

  ```
  drwx------ .helix/          -rw------- .helix/witness.json     -rw------- .helix/projects.json
  -rw------- .helix/metrics.jsonl  -rw------- .helix/audit.jsonl
  -rw------- .helix/ledger-mac-master.key   -rw------- .helix/memory.jsonl
  ```

  빈 디렉터리로 추출한 뒤 그 홈에 대해 번들을 구동하니 두 사실이 **등급까지 보존된 채**
  서빙되었다. `DATA[Verified:global]| m_2fe00555…`, `DATA[Fresh:global]| m_a3868b45…`.

- [x] **C2. 손상된 ledger**

  **C2a 잘린 꼬리 줄** — 개행 없는 조각 `{"v":1,"kind":"memo`를 덧붙였다. 두 사실이 등급까지
  보존된 채 서빙된다. README의 "다음 writer가 복구하고 잘린 조각은 건너뛴 줄로 격리된다"와
  일치한다.

  **C2b 중간 줄의 구조적 손상** — 두 번째 줄을 무효 JSON으로 바꾸었다. 그 사실이 사라지고,
  **손대지 않은 첫 사실의 등급도 `Verified`에서 `Fresh`로 떨어졌다.** 구분 실험으로 원인을
  특정하였다. 줄을 삭제해도 같은 결과가 나오므로 손상에 특유한 것이 아니라 행 집합의 변화에
  따른 것이며, 전체 출력에 다음 공시가 함께 나온다.

  ```
  (rollback witness mismatch: this ledger does not descend from its witnessed head;
   elevated grades are clamped to Fresh until an authorized re-baseline)
  ```

  MAC 입력을 확인한 결과(`src/memory/ledger-mac.ts:151-167`) 서명은 레코드 자신에 대해
  계산되며 행 집합에 의존하지 않는다. 따라서 등급 하락의 원인은 rollback witness이고, 이는
  README의 *Restoring* 절이 정확히 서술하는 설계된 동작이다. **결함이 아니다.**

  관찰(Minor): README의 *Corruption* 절은 "손상된 줄이 live view에서 제외된다"고만 적고 등급
  clamp를 언급하지 않는다. 그 절만 읽은 사용자는 다른 사실의 등급이 유지될 것으로 기대한다.
  두 절 사이의 상호 참조 공백이다.

- [x] **C3. master key 손실**

  `ledger-mac-master.key`를 삭제하였다. `Verified`가 `Fresh`로 되돌아가고 **두 사실의 내용은
  모두 살아남았다.** README의 "키를 잃어도 내용은 잃지 않으며 verify가 부여한 등급만
  영향받는다"와 일치한다.

  부기: 키 삭제 후 위트니스 note가 `scope not yet witnessed; the current head will be adopted`로
  바뀐다. 위트니스 검증이 같은 키 계통에 의존하므로 scope가 미목격 상태로 되돌아가는 것이며,
  보호할 상승 등급이 이미 없는 상태이므로 정합적이다.

- [x] **C4. soft erase 취소**

  playbook §3의 두 단계를 그대로 실행하였다.

  1. `helix_memory_inspect` with `history: true` — 삭제된 행이 **내용이 비워진 채** 렌더링된다.
     `DATA[erase:global:2026-08-19T07:06:02.058Z..2026-08-19T07:08:51.508Z]| m_a3868b45-… `
     문서가 "함정"이라 부른 그것이 그대로 재현된다.
  2. 첫 timestamp를 `asOf`로 넘기니 **내용이 온전히 돌아왔다.**
     `DATA[Fresh:global]| m_a3868b45-… the deploy runbook lives in docs/release`

  문서의 단서까지 확인되었다. `asOf`를 사실 자신의 `tx`로 주면 나중에 일어난 confirm이 아직
  없으므로 `Verified`였던 `m_2fe00555`가 `Fresh`로 렌더링된다. 문서는 이를 "스냅샷이 시간에
  대해 정직한 것이지 잃어버린 등급이 아니다"라고 적었고, 관측이 그대로이다.

**Block C 판정: 통과.** 네 여정 전부 문서가 지시한 명령으로 실행되었고 문서가 서술한 결과를
냈다. 실행되지 않는 명령은 없었다. 유일한 관찰은 C2b의 상호 참조 공백이며 Minor이다.
